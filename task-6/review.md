# 📋 Отчёт по ревью кода автотестов

> Файл: `bad_code.py`  ·  Сгенерировано скриптом `review_and_optimize.py`  ·  Автоматический статический анализ (модуль `ast`).

> ⚠️ **Важно:** исходный файл **не является валидным Python-кодом** (в телах функций пропущены отступы), поэтому `pytest` не мог его выполнить. Скрипт автоматически восстановил синтаксис перед анализом.

## ✅ Что сделано хорошо

1. Покрытие и позитивных (3 шт., ожидание 2xx), и негативных (2 шт., ожидание 4xx) сценариев.
2. Корректная отправка тела запроса через параметр `json=` (правильная сериализация и Content-Type).
3. Базовый URL вынесен в модульную константу `BASE_URL = 'http://localhost:8000'`.
4. В позитивных тестах проверяется не только статус-код, но и содержимое ответа (поле из тела).
5. Тесты автономны и не зависят друг от друга (нет общего изменяемого состояния) — хорошо для повторного и параллельного прогона.
6. Негативные тесты имеют говорящие имена: `test_create_user_invalid_email`, `test_create_user_missing_name`.

## ⚠️ Что сделано плохо / можно улучшить

**🔴 Неинтерпретируемый код.** В исходнике пропущены отступы в телах всех функций — файл физически не запускается (`IndentationError`). Это самая серьёзная проблема: автотесты просто не могут выполниться. Скрипт восстановил отступы.

### 1. 🟠 Дублирование кода в тестах  ·  приоритет: высокий

> **Обнаружено 3 тест(ов) с идентичной структурой, различающихся только данными (константами). Это классический случай для @pytest.mark.parametrize: тело одного теста заменяется параметризованным, а данные выносятся в список. Код становится короче и проще в поддержке.**

### 2. 🟡 HTTP-запросы без timeout  ·  приоритет: средний

> **5 из 5 запрос(ов) к requests выполняются без параметра timeout. При недоступном или зависшем сервере тест будет ждать неопределённо долго и «вешать» весь прогон. Рекомендация: добавить timeout (например, 5 секунд) в каждый запрос.**

### 3. 🟡 Захардкоженный путь эндпоинта  ·  приоритет: средний

> **Путь '/users' задаётся прямо в каждом из 5 запросов, а не хранится в константе. При изменении API придётся править его в N местах. Лучше вынести в модульную константу (например, USERS_ENDPOINT = f"{BASE_URL}/users").**

### 4. 🟡 Ассерты без поясняющих сообщений  ·  приоритет: средний

> **8 из 8 assert-ов не несут поясняющего сообщения. При падении сложно сразу понять, какое именно условие нарушилось и какие входные данные были задействованы. Рекомендация: добавлять message в assert.**

### 5. 🔵 Неиспользуемые импорты  ·  приоритет: низкий

> **Импортируются модули, которые в коде не используются: `pytest`. Лишние импорты создают иллюзию зависимости и раздражают линтеры.**

### 6. 🔵 Непоследовательное именование тестов  ·  приоритет: низкий

> **Имена с повторяющимися/артефактными токенами: `test_create_user_new_new_name`. Похоже на следы ручных переименований (copy/paste); такие имена хуже читаются в отчётах pytest.**

## 🔧 Ключевое улучшение: параметризация вместо дублирования

**Было** (3 почти одинаковых теста):

```python
def test_create_user():
    payload = {"name": "Alice", "email": "alice@example.com"}
    response = requests.post(f"{BASE_URL}/users", json=payload)
    assert response.status_code == 201
    assert response.json()["name"] == "Alice"

# ... и ещё 2 таких же с Bob и Charlie ...
```

**Стало** (1 параметризованный тест + сессия + timeout):

```python
USERS_ENDPOINT = f"{BASE_URL}/users"
REQUEST_TIMEOUT = 5

@pytest.fixture()
def api_client():
    with requests.Session() as session:
        yield session

@pytest.mark.parametrize("payload, expected_status, expected_name", [
    ({"name": "Alice", "email": "alice@example.com"}, 201, "Alice"),
    ({"name": "Bob", "email": "bob@example.com"}, 201, "Bob"),
    # ... и остальные данные ...
])
def test_create_user(api_client, payload, expected_status, expected_name):
    response = api_client.post(USERS_ENDPOINT, json=payload, timeout=REQUEST_TIMEOUT)
    assert response.status_code == expected_status, f"..."
    if expected_name is not None:
        assert response.json().get("name") == expected_name
```

## 📈 Сводная таблица «Было → Стало»

| # | Проблема | Было | Стало |
| --- | --- | --- | --- |
| 1 | Дублирование тестов | 5 отдельных функций | 1 `@pytest.mark.parametrize` (5 наборов данных) |
| 2 | Соединение | новый `requests.post` каждый раз | переиспользование `requests.Session` (fixture) |
| 3 | Timeout | отсутствует | `timeout=REQUEST_TIMEOUT` в каждом запросе |
| 4 | Эндпоинт | `f"{BASE_URL}/users"` в каждом тесте | константа `USERS_ENDPOINT` |
| 5 | Ассерты | без сообщений | с поясняющим сообщением и телом ответа |
| 6 | Импорт | `import pytest` (не используется) | реально используется (parametrize/fixture) |

## 🏁 Вывод

Исходный код выполняет свою задачу и покрывает как позитивные, так и негативные сценарии, но страдает от дублирования и не следует ряду стандартных практик автотестов: отсутствует timeout, эндпоинт захардкожен в каждом запросе, ассерты без поясняющих сообщений, соединение не переиспользуется, есть неиспользуемый импорт. Оптимизированный вариант сохраняет покрываемые сценарии, но делает код короче, надёжнее и проще в поддержке. Полная версия — в файле `optimized_code.py`.
